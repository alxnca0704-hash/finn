# Code Standards

## General

- Keep modules small and single-purpose.
- Fix root causes, do not layer workarounds.
- Do not mix unrelated concerns in one component, hook, or route.
- Components render UI, hooks talk to Convex, and `lib/` holds pure logic. Do not blur these three roles.
- Name things by what they are: `useGoals`, `DepositSheet`, `formatCurrency`. Avoid vague names like `utils2` or `helper`.
- Remove dead code and unused files instead of commenting them out.

## TypeScript

- Strict mode is required throughout the project.
- Avoid `any`. Use explicit interfaces or narrowly scoped types.
- Use the types generated by Convex (`Doc`, `Id`) instead of redefining them by hand.
- Validate unknown external input (forms, URL params, uploaded files) at system boundaries before trusting it.
- Money amounts are always integers in minor units. Convert to a display string only in `lib/` formatting helpers.
- Prefer union types for fixed values, for example `type TransactionType = "deposit" | "withdraw"`.

## Next.js

- Default to server components.
- Add `"use client"` only when browser interactivity requires it (forms, Convex hooks, Zustand, modals).
- Every component that needs `"use client"` lives in `components/client/`. Server components live in `components/server/`. Never mix the two in one folder.
- A file in `components/client/` must start with `"use client"`, and a file in `components/server/` must not.
- Pages stay server components and import client components from `components/client/` where interactivity is needed.
- Keep pages thin. A page composes components and does not hold business logic.
- Keep route handlers and layouts focused on a single responsibility.
- Use route groups to separate areas of the app:
  - `(auth)` for sign-in, sign-up, and onboarding. These screens share a simple centered layout with no app navigation.
  - `(app)` for signed-in screens such as goals list, goal detail, and profile and settings. These share the main app layout.
- Never hardcode paths in components. Import them from `constants/routes.ts`.

## Convex Hooks

- Components never call `useQuery` or `useMutation` with raw Convex function references. Wrap them in custom hooks inside `hooks/`.
- One hook file per domain: `use-goals.ts`, `use-transactions.ts`, `use-current-user.ts`.
- Hooks return a clear, stable shape, for example `{ goals, isLoading }` for reads and named action functions (`createGoal`, `deposit`, `withdraw`) for writes.
- Hooks handle the loading and error states of Convex calls, so components receive ready-to-render data.
- Hooks do not contain UI logic and do not import components.
- Do not copy Convex data into Zustand. Read it through hooks every time.

## Styling

- Use Tailwind utility classes for all styling.
- Use design tokens (CSS custom properties mapped into the Tailwind theme) for colors, spacing, and radius. No hardcoded hex values in components.
- Follow the border radius scale defined in `ui-context.md`.
- Extract repeated class combinations into a component, not a copied string.
- Build mobile first, then add larger breakpoints.

## API Routes and Convex Functions

- Validate and parse arguments with Convex validators (`v`) before any logic runs.
- Enforce auth and ownership before any read or mutation. Derive the user from the verified Clerk identity, never from a client-sent user id.
- Transactions have no update or delete mutation. Corrections are new transactions.
- Check business rules inside the mutation (amount greater than zero, withdrawal not above balance), not only in the form.
- Return consistent, predictable shapes and throw clear errors that the hook can turn into friendly messages.
- Keep each function focused on one job. Shared logic goes into helper functions inside `convex/`.

## Data and Storage

- Users, goals, and transactions belong in the Convex database.
- Profile pictures belong in Convex file storage. The database stores only the file reference.
- Do not store large content directly in database documents.
- Balance is derived from transactions and never saved as an editable field.
- Zustand holds temporary UI state only, such as open modals, selected goal, and form drafts.

## File Organization

- `app/(auth)/` — Sign-in, sign-up, and onboarding routes with their shared auth layout.
- `app/(app)/` — Signed-in routes: goals list, goal detail, profile and settings, with the main app layout.
- `components/client/` — All components marked `"use client"`: forms, deposit and withdraw sheet, modals, anything using hooks, Convex, or Zustand. Split by feature inside (`goals/`, `transactions/`, `auth/`).
- `components/server/` — Server components with no browser interactivity: static layouts, headers, empty states, display-only cards. Split by feature inside.
- `hooks/` — Custom hooks that wrap Convex queries and mutations, plus other shared React hooks.
- `convex/` — Schema, queries, mutations, and backend helpers.
- `constants/` — Fixed values: `routes.ts` for paths, plus limits (username length, max note length) and default currency.
- `lib/` — Pure helpers with no React and no Convex calls: currency formatting, date helpers, progress calculations, validation schemas.
- `stores/` — Zustand stores for client-only UI state.
